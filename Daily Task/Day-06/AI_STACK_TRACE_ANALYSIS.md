# Day 06 - AI-Assisted Debugging: Stack Trace Analysis & Verification Notes

## Overview
This document records two real-world stack traces generated by the `OrderProcessor` system, the AI (Copilot / Assistant) diagnostic analysis, and an evaluation verifying what the AI got right and where its explanation was incomplete or required nuance.

---

## Stack Trace 1: Chained Checked Exception (`OrderProcessingException` wrapping `InsufficientStockException`)

### Raw Stack Trace
```text
com.order.exception.OrderProcessingException: Order fulfillment failed during validation phase.
    at com.order.service.OrderProcessor.processOrder(OrderProcessor.java:70)
    at com.order.app.OrderApp.main(OrderApp.java:43)
Caused by: com.order.exception.InsufficientStockException: Requested 20 units of 'SUIT', but only 4 are available in warehouse.
    at com.order.service.OrderProcessor.processOrder(OrderProcessor.java:49)
    ... 1 more
```

### Prompt Given to AI Assistant:
> *"Analyze this stack trace. What caused the failure, where did it originate, and how should it be resolved in the order management pipeline?"*

### AI's Explanation:
> **AI Response:**
> "The failure was caused by an `OrderProcessingException` thrown at line 70 of `OrderProcessor.java`, which originated from `OrderApp.java:43`. However, the root cause is indicated by the `Caused by:` clause: an `InsufficientStockException` on line 49. The customer requested 20 units of 'SUIT', but only 4 units exist in the inventory map. To resolve this:
> 1. Add an inventory check before placing the order or suggest a backorder/partial order option.
> 2. Ensure that line 70 preserves the original cause so upstream handlers can inspect the requested vs available stock."

### Verification & Accuracy Audit:
- **What was Right:**
  - Accurately identified that line 70 is merely the wrapping point (`OrderProcessingException`) and the true origin is line 49 (`InsufficientStockException`).
  - Correctly parsed the message parameters (`Requested 20, Available 4`).
  - Recognized that the exception was properly chained using `initCause` / constructor cause chaining.
- **What was Missing / Incomplete:**
  - The AI did not highlight that line 70 was triggered inside a `multi-catch` block (`catch (InsufficientStockException | PaymentFailedException)`).
  - The AI did not observe that the `finally` block in `OrderProcessor` still executed successfully to log an audit rollback before line 70 bubbled up to `main`.

## Stack Trace 2: Unchecked Exception (`InvalidQuantityException`)

### Raw Stack Trace
```text
Exception in thread "main" com.order.exception.InvalidQuantityException: Order quantity must be positive. Received invalid quantity: -2
    at com.order.service.OrderProcessor.processOrder(OrderProcessor.java:42)
    at com.order.app.OrderApp.main(OrderApp.java:29)
```

### Prompt Given to AI Assistant:
> *"Why did this exception crash the thread and why is there no 'Caused by' clause?"*

### AI's Explanation:
> **AI Response:**
> "This is an unchecked runtime exception (`InvalidQuantityException extends RuntimeException`) thrown directly at `OrderProcessor.java:42`. There is no `Caused by:` clause because this exception is the direct root cause and was not caught and re-thrown wrapped inside another exception. The calling method at `OrderApp.java:29` failed to catch `RuntimeException`, causing the exception to reach the unhandled exception boundary of the main thread."

### Verification & Accuracy Audit:
- **What was Right:**
  - Correctly differentiated unchecked exceptions (`RuntimeException`) from checked exceptions.
  - Accurately explained the absence of `Caused by` (it was instantiated directly, not chained).
- **Nuance / Correction Required:**
  - In a production console menu or web controller, client-input validation errors should be caught at the presentation controller layer rather than letting them propagate to thread boundary, so the user can be prompted to re-enter a valid quantity without application crash.

---

## Summary of Exception Design Rules Enforced
1. **Preserve Root Causes:** Always pass the underlying `Throwable` to `super(message, cause)` when re-throwing wrapper domain exceptions.
2. **Never Swallow Exceptions:** Avoid empty `catch (Exception e) {}` blocks. Every catch block must log or re-throw.
3. **Audit Safety with `finally`:** Use `finally` to ensure resources (audit ledgers, database connections, locks) are closed regardless of normal or exceptional completion.
